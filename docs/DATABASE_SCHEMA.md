## The constraint that shapes everything

> **No table holds raw detected PII — nor a password, nor an email body.**

There is no `raw_text` column, no `detected_value`, no `original_text` — not nullable, not
optional, *not present*. `PiiEvent` stores the classification, confidence, reason, and a **masked**
preview (`XXXX XXXX 9013`). The original substring is matched in memory and discarded before the
response is built.

This is structural, not procedural. A future contributor cannot accidentally log an Aadhaar number
into a column that doesn't exist. Verified:

```
NO raw-PII columns present: True
```

Second-order detail: `pii_events.site_origin` stores `https://mail.google.com`, **not** the full URL.
Full URLs routinely carry PII in query parameters — storing them would reintroduce the exact leak the
table was designed to prevent.

The same rule was applied twice more when the stretch modules landed, and both times the *absence* is
the design:

- **`identity_checks` has `hash_prefix VARCHAR(5)`, not `hash`.** The column is physically too narrow
  to hold a SHA-1. Storing a password is not something a future edit can do by accident, because there
  is nowhere to put it — and the five characters that *are* stored were already public in the URL of
  the range lookup.
- **Module 3 has no table.** Email bodies contain other people's names, addresses, invoice numbers,
  and medical details — data the person pasting never consented on behalf of. `POST /phishing/analyze`
  therefore takes **no `db: Session` parameter at all**, which is a stronger guarantee than a policy
  of not writing: there is no session in scope to write with.

The second build (M8–M12) added no tables either, and in three cases the absence is again the design:

- **Module 11 has no table, for a sharper version of Module 3's reason.** A chat message is not just
  someone else's data, it is someone else's *conversation*, and the feature can be pointed at a thread
  the user is only half a participant in. `POST /scam/analyze` takes no session, and a test enumerates
  every table and asserts zero new rows after an analysis. The visible cost is stated rather than
  hidden: chat analysis therefore does **not** move the risk score, because nothing it learns is
  written down. That is a deliberate trade, not an oversight.
- **Module 12 adds no column.** An OCR'd screenshot produces exactly what typed text produces — a
  `pii_events` row with a classification and a masked preview. The image itself never reaches the
  backend at all, so there was never anything to find a home for.
- **Module 9 writes a `SiteCheck` and nothing else.** A QR code that resolves to a web address is a
  site visit about to happen, so it goes through the same `persist_site_check` with the same reasons
  the site engine writes for a page the user navigated to — indistinguishable by design, and correct
  for the Browsing sub-score, which cares about where the user was headed and not which gesture
  started it. A **UPI** QR has no domain, so **nothing is written** rather than a fabricated row. There
  is deliberately no `came_from_qr` column: adding one purely so the seed could look richer would put a
  fact in the database that the running product cannot produce.

## Tables

### `devices` — 3 columns

| Column | Type | Notes |
|---|---|---|
| `id` | `str(64)` PK | Random UUID generated by the extension on first run |
| `created_at` | datetime(tz) | |
| `last_seen_at` | datetime(tz) | `onupdate=utcnow` |

The MVP's stand-in for a user account. The extension sends it as `X-Sentinel-Device-Id`.

**Why a table at all, if there's no auth?** Because it's the seam. Turning on JWT means adding a
nullable `user_id` FK *here* — every other table already hangs off `device_id`, so accounts become an
additive migration rather than a rewrite of the event tables. Building this now costs one table and
makes "auth is a dependency swap" a true statement instead of a hopeful one.

### `pii_events` — 12 columns · Module 1

| Column | Type | Notes |
|---|---|---|
| `device_id` | FK | |
| `occurred_at` | datetime(tz) | |
| `site_origin` | `str(255)` | Origin only, never full URL |
| `field_kind` | `str(32)` | `input` / `textarea` / `contenteditable` / `paste` / `image` |
| `pii_type` | `str(40)` | `aadhaar`, `credit_card`, … |
| `risk_level` | `str(16)` | low / medium / high / critical |
| `confidence` | float | |
| `detection_tier` | `str(16)` | `regex` / `llm` / `ocr` |
| **`reason`** | `str(500)` **NOT NULL** | Explainability, enforced at the DB layer |
| `masked_preview` | `str(120)` | Masked form only |
| `action_taken` | `str(16)` | none / masked / ignored / allowlisted |

**`reason` is `nullable=False` deliberately.** Your spec says every prediction must carry a reason.
Making it a required column means a bare verdict is *unwritable* — the rule is enforced by the
database, not by everyone remembering.

**`detection_tier` is persisted rather than inferred.** It's the evidence for the hybrid-architecture
claim, and it lets you answer *"how often did the LLM tier actually earn its latency?"* from real demo
data. That's a good answer to have ready when a judge asks why not just call the LLM.

**`field_kind` gained two values that are not element types, and that is the point.** `paste` and
`image` answer a different question from `input` and `textarea`: not *what kind of box was it* but
*how did this nearly leave you*. That distinction is load-bearing rather than decorative —

- a value that was **pasted** was never composed by the user. They copied it out of a terminal or a
  password manager and dropped it somewhere. That is the single most common way a credential leaks, and
  it is the only case where the destination matters as much as the value (M10);
- a value found in an **image** was never typed at all. It was printed on a photograph the user was
  about to attach, and a text scanner is blind to it (M12).

The dashboard renders the difference in words. `routers/dashboard.py` maps `paste → "pasted into"` and
`image → "found in an image on"`; the three HTML element kinds deliberately fall through to a plain
`"caught on"`, because leaking the string `contenteditable` into a sentence written for a senior citizen
would be worse than saying less.

**`detection_tier = "ocr"` is not a third detector.** It is the regex tier run a second time over text
whose confusable characters were corrected — and only where Verhoeff or Luhn confirmed the correction
afterwards. It is recorded distinctly because "the tool changed a digit before it matched" is exactly
the kind of fact that must survive into the row rather than being flattened into `regex`. The UI says
so out loud, and the confidence on such a row is capped at `0.80` and drops per corrected character, so
the number itself reports how much inference went into it. Row-level proof of this lives in the seed:
an OCR-recovered Aadhaar at `0.75` sits alongside a typed one at `0.98`.

`String(16)` holds all three values with room to spare, so `DetectionTier` gaining a member was an
enum change with no migration. The enum is nonetheless kept in sync by hand with the literal in
`services/pii/ocr_normalise.py`, which cannot import it: nothing under `services/pii/` imports the ORM,
so the whole detection engine stays testable with no database in the process.

**`action_taken = allowlisted` is your false-positive metric.** Every one is a user telling you the
detector was wrong. Free ground truth, and a credible roadmap slide: *"we know our FP rate because
users report it in one click."*

Index: `(device_id, occurred_at)` — every timeline and "last 24h" query filters and sorts on exactly
this pair.

### `site_checks` — 10 columns · Module 2

| Column | Type | Notes |
|---|---|---|
| `domain` | `str(255)` | |
| `trust_score` | int | 0–100 |
| `verdict` | `str(16)` | safe / suspicious / dangerous / **unknown** |
| `reasons` | JSON | Itemised trigger list |
| `domain_age_days` | int **NULL** | NULL = RDAP had no answer |
| `safe_browsing_hit` | bool **NULL** | NULL = not checked / API down |
| `brand_mismatch` | bool | |

**The nullable columns are the important design here.** RDAP 404s on some ccTLDs; Safe Browsing may be
keyless or rate-limited. `NULL` means *"this signal was unavailable"*, which the risk engine handles by
redistributing weight — **never** by defaulting to safe. `SiteVerdict.UNKNOWN` exists for the same
reason: "we couldn't tell" and "it's fine" are different answers, and collapsing them is how a security
tool lies to its user.

`reasons` is JSON rather than a child table because it is always read whole and never queried into. A
join would buy nothing.

### `identity_checks` — 9 columns · Module 4

| Column | Type | Notes |
|---|---|---|
| `device_id` | FK | |
| `occurred_at` | datetime(tz) | Newest per key wins — see supersession below |
| `hash_prefix` | `str(5)` **NOT NULL** | Five hex chars, uppercased. **Physically cannot hold a full hash.** |
| `label` | `str(40)` NULL | The user's own nickname — "Gmail", "Old forum login" |
| `breach_count` | int **NOT NULL** | `0` means *checked, not found*. Distinct from no row at all |
| `risk_level` | `str(16)` **NOT NULL** | low / high / critical |
| `confidence` | float **NOT NULL** | `0.95` corroborated · `0.75` contradicted |
| **`reason`** | `str(500)` **NOT NULL** | Same DB-enforced explainability rule as `pii_events` |

**Rows accumulate, but scoring supersedes.** `current_checks()` collapses history to one row per
lowercased `label` (or per prefix when unlabelled) and only the newest counts. History is kept because
deleting it would erase the evidence that the user *fixed* something; scoring ignores it because
otherwise there is no action a user can take that improves this number, and a score you cannot move is
a score people stop reading. Check "Gmail" → breached → change it → re-check "Gmail" → clean → the
Identity sub-score recovers on the next dashboard load.

**Identity is the one component that does not time-decay**, and it is not filtered by the 30-day
window either. A breached password is not behaviour that ages — it stays true until the credential
changes. Decaying it would let the score recover because the user *waited*, which teaches exactly the
wrong lesson.

Index: `(device_id, occurred_at)` — the score query fetches all of a device's checks and sorts them.

### `score_snapshots` — 7 columns · Module 6

`overall`, `privacy`, `identity`, `browsing` + `captured_at`.

Denormalised on purpose. Recomputing score history from raw events on each dashboard load is slower
**and wrong**: it would retroactively rewrite history every time you tune the scoring weights, so the
trend chart would silently change shape mid-hackathon. A snapshot records what the score *was*.

## What is deliberately absent

| Not built | Why |
|---|---|
| `users`, `passwords` | No accounts in MVP. `devices` is the seam. And "no `passwords` table" is permanent, not an MVP shortcut — see `identity_checks`. |
| `emails` / `phishing_analyses` | Module 3 stores nothing. The endpoint has no DB session. |
| `chat_messages` / `scam_analyses` | Module 11, same rule, stronger case — a chat thread is someone else's conversation. No session; a test enumerates every table and asserts zero rows after an analysis. |
| `qr_scans` | A QR that resolves to a URL is a `site_checks` row like any other. A UPI QR has no domain, so nothing is written rather than a row invented to fill the gap. |
| `screenshots` / `ocr_text` | The image never reaches the backend. Only the extracted text is classified, and only the classification survives — a `pii_events` row identical in shape to a typed one. |
| `narratives` | Module 8 is derived from rows that already exist. Storing a sentence would let it disagree with the score it explains. |
| `allowlist` table | Per-site overrides live in `chrome.storage.local` — private, offline, and they must work when the backend is down. |
| `recommendations` | Computed from current state on read. Storing them means staleness bugs. |
| Alembic migrations | Schema is only ever created fresh. Changed a column? `rm sentinel.db` and re-seed — two seconds. |

`init_db()` uses `create_all`, which does **not** alter existing tables. Stated plainly because it will
bite exactly once, at the moment you add a column.
